# A wildcard cascade crosses the iteration bound

Section 12.4 requires the implementation to "detect nonterminating or excessively expanding rule
sets", to "enforce configurable generated-entry and iteration limits", and to "report the rules
responsible for the limit". This case is the second and third of those: a rule set that expands one
level per wave, run under a bound that stops it partway, with the report naming the rules that spent
the bound.

## The rule set

```text
a.x=1
a.*.b=2
a.*.*.c=3
a.*.*.*.d=4
```

Section 12.4 defines a wave as one pass that "evaluates eligible `(rule,item)` pairs against the
items present at the start of that wave; items generated during the wave become eligible in the next
wave", and it fixes eligibility by depth: "If the rule's last wildcard-containing part is at depth
`k`, eligible items are the distinct depth-`k` prefixes of existing paths".

The three rules have their last wildcard-containing part at depths 2, 3 and 4 respectively, and each
one's output is exactly one level deeper than its own wildcard depth. So each rule's product is the
next rule's only eligible item, and no two of them can run in the same wave:

| Wave | Items at wave start | Rule that can match | Generated |
|---|---|---|---|
| 1 | `a.x` | `a.*.b` | `a.x.b` |
| 2 | `a.x.b` | `a.*.*.c` | `a.x.b.c` |
| 3 | `a.x.b.c` | `a.*.*.*.d` | `a.x.b.c.d` |
| 4 | — | none | — |

This is the shape Section 12.4 calls "excessively expanding": every wave produces the item that
justifies another wave, and only the length of the ladder — not anything the fixed point can observe
early — decides when it stops. A rule set written with a longer ladder, or generated by a template
family, expands as far as it is allowed to. That is what the bound is for.

## Why the bound is 2

Section 12.4: "Breadth-wave iteration counts apply only to generative templates." A wave that
generates nothing is the observation that the fixed point has been reached, not a step toward it, so
it is not charged. Waves 1, 2 and 3 each generate; wave 4 does not.

`--max-wildcard-iterations 2` therefore admits waves 1 and 2 and refuses wave 3. Setting it to 3
admits the whole cascade, which is the companion case
`wildcard-cascade-completes-within-the-iteration-bound`. Together they assert that the number is a
threshold: an implementation that never charged, or that charged the settling wave as well, fails one
of the two.

## Which rules are responsible

"Report the rules responsible for the limit." At the moment wave 3 is refused, `a.*.b` and
`a.*.*.c` have each generated, and `a.*.*.*.d` has not — it is the rule that was about to run, not
one that consumed anything. Blaming it would point the reader at the rule that is cheapest to
delete and hide the two that actually built the ladder; blaming every declared rule would make the
field carry no information at all in a file that declares many.

The report therefore names the two rules that have generated, in source order, each identified by
source and line as every rule-bearing diagnostic is.

## Exit and output

Appendix B maps a crossed wildcard bound to `WILDCARD002` and exit code 1. The fixture carries no
`expected/` directory, which asserts that the run stages nothing: Section 15.1 places output
planning after the fixed point, so a run that never completed step 10 has nothing to plan.
