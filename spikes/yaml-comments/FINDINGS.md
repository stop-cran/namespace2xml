VIABLE WITH COMPENSATION

# YAML comment spike findings

## 1. Verdict

YamlDotNet 16.3.0 is sufficient for parsing structure and exposes enough `Mark`
data to associate comments deterministically, but the `Parser` event stream is
not by itself a complete source of comment tokens:

- a comment-only stream emits only its first `Comment` event and then
  `MoveNext()` returns `false`;
- comments following an explicit `...` can be truncated (explicit markers are
  already rejected by the product specification);
- comments on a bare root scalar, flow collection, or block scalar are reported,
  but `Comment.IsInline` is incorrectly `false`.

No hand-written YAML scanner is required. A second YamlDotNet
`Scanner(reader, skipComments: false)` pass reports all tested comment tokens,
including the parser omissions, with exact source marks. Use scanner comments as
the authoritative token inventory and parser events as the authoritative
structure.

The executable corpus contains 28 documents, 74 real comments, and 8 `#`
controls that must remain scalar content. All 82 expectations pass. The full
event streams and associations are in `run-output.txt` and are regenerated by
`dotnet run`.

## 2. Normative comment requirements

### Round trip and common model

**Section 3.3, “Normalized same-format round trip”:**

> For supported features, reading and writing the same format must preserve:
>
> - data structure;
> - scalar type;
> - key and item order;
> - supported comments;
> - supported XML node kinds;
> - significant XML text and whitespace;
> - namespace names.

> Unsupported source concepts are discarded during rendering and must produce
> one summarized warning per output file and feature category. For example,
> rendering YAML comments to JSON produces one comments-discarded warning, not
> one warning per comment.

**Sections 4.1 and 4.2:**

> A document contains:
>
> - a root value;
> - ordered comments and source annotations;
> - source identity and source ordering;
> - format-specific metadata within the supported subset.

> One logical path may simultaneously retain:
>
> - an optional scalar or null payload;
> - an explicit mapping-presence contribution, including an empty mapping;
> - ordered mapping children;
> - an optional ordered sequence of stable ordering values;
> - comments and source annotations;
> - format-specific node-kind metadata.

**Section 4.5, “Comments”:**

> A non-XML comment records:
>
> - text;
> - source order;
> - association with a logical qualified path, sequence ordering value, or
>   document position;
> - whether it was leading, inline, or trailing where the source format
>   distinguishes those positions.

> Exact whitespace surrounding a comment need not be preserved.

> Normalized association rules are:
>
> - a leading comment binds during parsing to the logical path or sequence item
>   of the immediately following entry;
> - an inline comment belongs to the entry or item on the same logical line;
> - a trailing comment belongs to the immediately preceding entry or item;
> - document-leading and document-trailing comments have no value owner;
> - comments contributed to the same surviving logical path accumulate in
>   source order;
> - when several YAML inline comments accumulate at one path, the latest remains
>   inline and earlier inline comments become leading comments in source order;
> - overriding a payload or container contribution does not detach comments
>   already bound to that logical path;
> - the winning contribution determines the final output position of the logical
>   path, and its bound comments move with it;
> - permanent ignore masks remove the matching path and all comments bound to it;
> - output-view `type=ignore` hides the matching path and its bound comments in
>   that output instance;
> - comments on a wildcard template are cloned onto each generated contribution
>   in match order;
> - standalone XML comments remain ordered content nodes and are not reassigned
>   to adjacent values.

> When a transformation re-addresses a value—such as `key` record construction,
> mixed-key `type=array`, input or destination `append`, or another
> rebase—comments bound to the source path or sequence item move with that value
> to its new address. Document-position comments do not move.

**Section 5.2, “Mapping order after override”:**

> Overriding a mapping key moves that exact key, together with comments bound to
> it, to the winning contribution's position mark.

> The same rule applies to comments: refreshing an ancestor's shape-mark through
> a descendant does not move that ancestor or comments bound to the ancestor
> path.

**Section 6.2:**

> `--max-comments` — Maximum retained comments. Default: 1,000,000.

> `--max-comment-bytes` — Maximum total decoded comment bytes. Default: 256 MiB.

### Input formats

**Section 8.5, “Comments” (namespace input):**

> A namespace comment is a physical line whose first non-whitespace character is
> an unescaped `#`. A `#` elsewhere in a name or value is an ordinary character.

> Consecutive comments are associated with the next entry. Trailing comments
> with no following entry remain document-trailing comments.

> The association is made with the following entry's logical qualified path
> before overrides are evaluated. It therefore survives replacement of that path
> and moves to the winning contribution's output position as specified in
> Sections 4.5 and 5.2.

**Section 9.2:**

> JSON comments are not supported.

**Section 10.1, “Supported features”:**

> YAML input supports:
>
> - ordered mappings;
> - sequences;
> - strings;
> - integers;
> - decimals;
> - Booleans;
> - null;
> - leading, inline, and trailing comments.

> Every conforming YAML parser must expose these supported comment positions.
> Comments are retained in the common model and emitted by YAML output after
> normalized formatting.

> These rules, rather than an underlying library's advertised YAML 1.1 or 1.2
> mode, are normative. Any parser may be used only if it is configured or wrapped
> to produce exactly `RestrictedYaml1` behavior.

**Section 10.2, “Deliberately unsupported features”:**

> This version does not preserve:
>
> - anchors;
> - aliases;
> - custom tags;
> - directives;
> - explicit document markers such as `---` and `...`;
> - exact scalar quote style;
> - folded-versus-literal multiline style;
> - exact indentation;
> - exact comment spacing.

> Anchors, aliases, and every explicit tag token—including standard `!!` tags,
> verbatim tags, and local tags—are blocking input errors in this version,
> regardless of whether the tag would preserve the same basic value.

**Section 10.3, “Multiple documents”:**

> Multiple YAML documents in one input stream are not supported in this version.

> Encountering any explicit document marker is an error.

**Section 11.5, “XML comments”:**

> XML comments are retained as ordered comment nodes.

> They are not forced into a "leading comment for the next value" representation
> because a comment may occur between mixed-content nodes or after the final
> child.

### Options, merge, and transformation

**Section 16.5, `key`:**

> comments bound to the original child path move with the complete generated
> record, while the generated key field itself receives no separate comment;

**Section 16.6, `type=ignore`:**

> Removes the complete matched overlay subtree, including payload, all container
> projections, descendants, and comments, from the selected output instance
> only.

**Section 16.8, YAML input options:**

> `PreserveComments`, enabled by default.

**Section 16.9, YAML output options:**

> Supported flags:
>
> - `PreserveComments`;
> - `DiscardComments`.

> `PreserveComments` and `DiscardComments` are contradictory.

> Default: `PreserveComments`.

> YAML document separators and alternate multiline-style preservation are not
> supported in this version.

**Section 17.1, “General deep merge”:**

> non-XML comments bind to logical paths rather than individual scalar or shape
> contributions; they accumulate and survive merge whenever their logical path
> survives. Shape-conflict projection attaches them to the surviving projection.
> They are omitted only when the logical path is absent from that output through
> permanent masking, non-selection, `type=ignore`, or replacement of an ancestor
> that removes the path.

**Section 17.5, cross-format replacement:**

> A cross-format replacement discards the complete accumulated plan for that
> destination, including document data, comments, renderer state, sequence
> provenance, and every destination high-water mark.

### Output and cross-format behavior

**Section 19.1, namespace output:**

> Comments are emitted as normalized `# comment` lines where their association
> can be represented.

**Section 19.3, JSON output:**

> renders comments nowhere and emits a summarized discard warning when comments
> exist;

**Section 19.4, YAML output:**

> YAML output:
>
> - preserves mapping and sequence order;
> - preserves supported scalar types;
> - emits retained comments in normalized positions;
> - uses literal block scalars for multiline values;
> - does not emit `---`;
> - does not preserve original quote style, tag syntax, anchors, aliases, or
>   folded-versus-literal source style;
> - applies structural merge before serialization.

**Section 20, “Comments across formats”:**

> Comments are preserved when both the source and destination support the common
> comment association:
>
> | Destination | Comment behavior |
> |---|---|
> | namespace | Emit normalized leading `#` comments. |
> | quotednamespace | Emit normalized leading `#` comments. |
> | YAML | Emit normalized leading, inline, and trailing comments where representable. |
> | XML | Emit ordered XML comments where representable. |
> | JSON | Discard with summarized warning. |
> | INI | Emit only when enabled by `inioutputoptions`; otherwise discard with summarized warning. |

> Cross-format comment association follows source order:
>
> - a comment before the first payload or item is document-leading;
> - a comment between two payloads or items becomes a leading comment of the
>   following payload or item;
> - a comment after the final payload or item is document-trailing;
> - inline YAML comments remain attached to their payload;
> - when several source documents merge, document-leading comments precede that
>   source's first surviving contribution and document-trailing comments follow
>   its final surviving contribution.

> Converting YAML comments to XML or XML comments to YAML uses these associations.
> Exact lexical spacing is not guaranteed.

**Section 22:**

> `WARN003` — Unsupported metadata/comment discarded or normalized — once per
> feature category and output file.

**Section 23:**

> parsed node, comment, and comment-byte totals are accumulated at the parse-phase
> join in CLI source order as specified in Section 7.3;

> Accounting occurs before allocation or expansion whenever possible. XML node
> creation, wildcard generation, comments, and serialized output buffers all
> consume the corresponding global budget.

**Section 25.10:**

> The comment remains bound to logical path `a`, and the winning `a`
> contribution determines their final position.

**Section 26 requires automated tests for:**

> 10. Winning-source mapping order and logical-path comment movement across
> overrides.

> 13. YAML comment input and output.

> 17. Cross-format metadata-loss warnings.

> 34. Permanent ignore masks across concrete input, wildcard generation,
> references, selectors, and comments.

> 57. Output-option defaults, XML declaration control, and comment-option
> enablement.

**Section 27 defers:**

> - JSON comments;
> - YAML document separators and multiple documents;
> - preservation of YAML anchors, aliases, tags, quote style, or multiline style;
> - exact lexical round trips;

## 3. Association rule

The implemented rule is:

1. Parse with `new Parser(new Scanner(reader, skipComments: false))`.
2. Build the complete mapping/sequence tree from non-comment parser events.
   Record each mapping entry and sequence item path, owning collection,
   indentation, and value start/end marks. Do **not** use event adjacency:
   YamlDotNet can emit a comment before the value event it lexically follows.
3. In a second pass, enumerate `YamlDotNet.Core.Tokens.Comment` from
   `Scanner(skipComments: false)`. Match scanner tokens to parser comments by
   `Start.Index`. The scanner list is authoritative when the parser list is
   incomplete.
4. For each comment, derive inline ownership lexically:
   - construct anchors for mapping keys, scalar/alias values, collection starts,
     flow collection closes, sequence items, and the root value;
   - among anchors on the comment's physical line and before `#`, choose the
     rightmost anchor; break equal-position ties by later structural event, which
     makes a comment after `}` or `]` belong to the enclosing entry rather than
     its last child;
   - if there is no same-line anchor but the scanner says inline and the next
     structural value is a sequence item, the comment follows a dash-only item
     header and belongs to that item.
5. For a full-line comment:
   - before the root payload, classify it as document-leading;
   - otherwise, if the immediately following entry or pending scalar value is at
     the same or deeper indentation, classify it as leading for that entry/item;
   - if the next entry dedents, select the deepest still-open collection whose
     entry indentation is no deeper than the comment and classify it as trailing
     for that collection's preceding entry/item;
   - at root scope with no following entry, classify it as document-trailing;
   - in a comment-only stream, retain it as ownerless document-position metadata.
6. Blank physical lines do not change ownership. They are observable as gaps in
   `Mark.Line`, and exact whitespace is explicitly non-normative.
7. Process comments independently in `Start.Index` order. Consecutive comments
   therefore retain source order while receiving the same owner when applicable.

This resolves the nested-boundary case:

```yaml
parent:
  child: 1
# column 1: leading for the next parent entry
next: 2

other:
  child: 3
  # column 3: next entry dedents, so trailing for other.child
final: 4
```

YAML itself does not define semantic comment ownership. The same-or-deeper rule
is the deterministic product convention inferred from Sections 4.5 and 20.
YamlDotNet preserves the column needed to apply it.

## 4. Position matrix

| Comment position | Parser reports it? | Association unambiguous? | Notes |
|---|---:|---:|---|
| Leading before top-level mapping key | Yes | Yes | Next same-level entry. |
| Leading before nested mapping key | Yes | Yes | Path and collection come from parser structure. |
| Leading before sequence item | Yes | Yes | Sequence item path is known; dash indentation is retained/inferred. |
| Inline after scalar mapping value | Yes | Yes | Same-line scalar end anchor. |
| Inline after key with nested block value | Yes | Yes | Key anchor owns it even though `MappingStart` follows later. |
| Inline after scalar sequence item | Yes | Yes | Same-line item value. |
| Inline after dash-only nested/empty item | Yes | Yes | `IsInline=true`; next item value identifies the item. |
| Multiple consecutive leading lines | Yes, all | Yes | Each token retains source order. |
| Blank line between comment and entry | Yes | Yes | No blank event, but `Mark.Line` exposes the gap; ownership is unchanged. |
| Very top, before content | Yes | Yes | `DocumentStart` may appear before it in event order; marks place it first. |
| Very end, after content | Yes, all | Yes | Includes multiple lines and no final newline. |
| Between nested last child and parent sibling | Yes | Yes under the stated rule | Comment column distinguishes parent-leading from child-trailing. |
| Inline/full-line in flow mapping | Yes | Yes | Inner entry and post-`}` cases both work. |
| Inline/full-line in flow sequence | Yes | Yes | Inner item and post-`]` cases both work. |
| Around `---` / `...` | Incomplete | Not needed | Parser loses later post-`...` comments; Section 10.3 rejects the file. Scanner sees them. |
| `#` inside quoted scalar | No, correctly | Yes | Remains scalar content, including multiline quotes. |
| `#` in plain scalar without preceding whitespace | No, correctly | Yes | Remains scalar content. |
| Comment after `|`, `>`, and chomping/indent indicators | Yes | Yes | Header comment belongs to owning entry/root. |
| `#` line inside block scalar body | No, correctly | Yes | Included in scalar value text. |
| Around anchors, aliases, and tags | Yes | Yes | Association works, but Section 10.2 requires a blocking input error. |
| Inline comment on a bare root scalar | Yes, `IsInline=false` | Yes with marks | Do not trust `IsInline`. |
| Inline comment after root flow collection | Yes, `IsInline=false` | Yes with marks | Closing collection anchor identifies root. |
| Inline comment on root block-scalar header | Yes, `IsInline=false` | Yes with marks | Scalar start mark identifies root. |
| Comment-only document | Only the first | No from parser alone | Scanner reports all comments; synthesize/retain ownerless document metadata. |
| CRLF input | Yes | Yes | Line, column, and index remain correct. |
| Comment before an indented scalar value | Yes | Yes | Pending mapping entry or sequence item owns it. |

## 5. Limitations and minimal reproductions

### 5.1 Parser truncates comment-only streams

```yaml
# first

# second
```

Observed parser events: `StreamStart`, first `Comment`, then `MoveNext() == false`.
There is no second `Comment`, `DocumentStart`, `DocumentEnd`, or `StreamEnd`.
The scanner emits both comments and `StreamEnd`.

### 5.2 Parser truncates comments after explicit document end

```yaml
a: 1
... # first post-end comment
# second post-end comment
```

The parser emits the first post-end comment and then stops; the scanner emits
both. This is not a conforming-input blocker because Section 10.3 requires an
error for `...`.

### 5.3 `Comment.IsInline` is false on root values

```yaml
value # root inline
```

The comment is reported at the correct line/column/index but with
`IsInline=false`. The same occurred for:

```yaml
[one, two] # root flow inline
```

and:

```yaml
| # root block-scalar header
  body
```

Same-line marks recover the correct classification.

### 5.4 Event order is not lexical order

Examples observed:

- `DocumentStart` precedes a document-leading `Comment`;
- a block-scalar header comment precedes the corresponding `Scalar` event;
- a comment after an empty value precedes the empty `Scalar` event;
- comments after an anchor can precede the anchored `MappingStart`.

Therefore “attach to the previous/next parser event” is incorrect. Build the
structure first and associate by marks.

### 5.5 Blank lines have no event

```yaml
# comment

key: value
```

There is no blank-line event. The comment end and key start line numbers differ
by two, so the separation remains detectable. This loses no required data because
Section 4.5 says exact surrounding whitespace need not be preserved.

### 5.6 Comment ownership is a product rule, not YAML semantics

YAML treats comments as presentation and ignores indentation on comment-only
lines for structure. The parser cannot supply an intrinsic “owner” because YAML
has none. It does retain source order, line, column, and structural events, which
are sufficient to apply the deterministic rule in Section 3 above. The main
semantic risk is changing that convention later, not loss of source information.

## 6. Compensating pass

Use two YamlDotNet passes over the already-decoded source text:

1. `Parser(Scanner(..., skipComments:false))` for the structural event tree.
2. `Scanner(..., skipComments:false)` for the authoritative comment token list.

Match by `Comment.Start.Index`; scanner and parser marks were identical for every
comment both reported. The compensating token collector is approximately
30–50 production lines. A production-quality association layer is approximately
150–220 lines plus tests. It is not a hand-written YAML scanner.

Main risks:

- accidentally counting comments twice against resource limits;
- relying on parser event order rather than marks;
- treating `IsInline` as authoritative;
- associating comments from a syntactically rejected document before reporting
  its blocking parse error;
- retaining two decoded copies of large input instead of reusing one string.

If the implementation refused a second YamlDotNet scan, a hand-written lexical
recovery scanner would need to understand quoted scalars, flow collections,
block-scalar headers and bodies, document markers, CRLF, and no-final-newline
input. That is roughly 300–500 lines and materially riskier; the evidence does
not justify it.

## 7. What this means for the implementation plan

Keep YamlDotNet 16.3.0. Add a small `CommentTokenCollector` based on the
YamlDotNet scanner, then run the mark-based association pass after the parser has
built logical paths and sequence items. Reject markers, anchors, aliases, and
tags as required before merge. Port this corpus into automated Core tests,
including the two parser omissions and root-inline `IsInline` regressions.

Run the spike from the repository root with:

```powershell
dotnet run --project spikes\yaml-comments\YamlCommentSpike.csproj
```
